# GDT289 — cross-host wrapper-position transfer

## Question

GDT286 found that an exact opaque `PAGE_HOST` helps predict wrapper identity and
that the exact `host × within-field-position` cell adds another 0.032 bits per
event.  Is that interaction generated by a compact position rule shared across
many hosts, or does it require a separate lookup table for each host-position
cell?

This experiment tests only the formal renderer.  Hosts are opaque IDs.  Their
glyph substrings, meanings, sounds, morphology, and semantic roles are not
used.

## Frozen panels and split

Use the same eight 8,448-event, f84-free panels as GDT286.  Assign every exact
host to one of eight immutable buckets with
`SHA256("GDT289_HOST_BUCKET|panel|host") mod 8`.

For every held physical folio and target event, the target host's wrapper
profile at the target position is forbidden.  A row is scoreable only when the
same host occurs on another physical folio in at least one *different*
within-field position.  The position-transfer tables are learned only from
hosts outside the target host bucket and from folios outside the held folio.
Thus the model may recognize an opaque target host from other positions, but
cannot learn that host's target-position cell or use its host family when
learning the cross-position rule.

## Frozen predictors

Wrapper probabilities use Dirichlet-1/2 global smoothing and the fixed
11-event hierarchical prior used by GDT286.

1. `POSITION_CONTEXT`: section, Currier, hand, register, target position, host
   length, first host character, and last host character.  No target-page
   wrapper outcome, including an earlier event, enters any predictor.
2. `OTHER_POSITION_HOST_BAG`: the target host's wrapper counts on training
   folios at all positions except the target position, shrunk to
   `POSITION_CONTEXT`.
3. `CROSS_HOST_POSITION_TRANSFER`: for every ordered source-position to
   target-position pair, learn a host-equal wrapper-profile transition table
   from non-target-bucket training hosts.  Apply those tables to the target
   host's observed other-position profiles, average forecasts weighted by
   source-position occurrence count, and give the forecast the same effective
   count as `OTHER_POSITION_HOST_BAG` before the same 11-event shrinkage.

The primary effect is
`OTHER_POSITION_HOST_BAG bits - CROSS_HOST_POSITION_TRANSFER bits` on held
physical folios.  Report per-position, per-host-bucket, per-folio, held-section,
and held-hand sensitivities for Voynich.  Alternate readings remain
sensitivities, not replications.

## Frozen null

Freeze the two fully training-only held-folio probability vectors for every
scoreable event, then
in each world permute the held wrapper outcomes within exact
`physical folio × section × Currier × hand × register × target position × host
length × first host character × last host character` strata.  This preserves:

- the exact scored host inventory and position support;
- the training-learned host-bag and transfer forecasts;
- held-folio wrapper counts within every exact nuisance/opportunity stratum;
- folios, registers, positions, host length, and host edge shape.

It destroys the alignment between the target host and its held wrapper outcome
while leaving both competing training-only predictors fixed.  Use 64 shared
worlds with seed family
`GDT289_HELD_WRAPPER_ALIGNMENT|panel|world|stratum`.
Report local and standardized max-eight inclusive p-values.

## Frozen decision

Call `LOW_COMPLEXITY_CROSS_HOST_POSITION_RULE_SUPPORTED` only if Voynich:

- has positive primary gain;
- has positive gain in at least six of eight target-host buckets;
- has positive gain in at least three of four target positions;
- has max-eight `p <= .05`; and
- has positive gain in both held-section and held-hand sensitivities.

Otherwise call `HOST_POSITION_EFFECT_REQUIRES_HOST_SPECIFIC_TABLE`.  If fewer
than 1,000 Voynich events are scoreable, call
`INSUFFICIENT_CROSS_POSITION_HOST_CAPACITY`.

## Claim ceiling and seal

At most this establishes a reusable opaque wrapper-position rule across host
identities.  It cannot identify morphology, a lexical class, a grammatical
function, abbreviation, sound, language, meaning, plaintext, or translation.
Only the published f84-free native event inventory is read.  No f84 row may be
opened, parsed, retained, joined, or scored.
